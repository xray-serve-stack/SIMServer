# SIMServer

SIMServer is the server-side component of the SIMServe system.

It maintains WebSocket connections with SIMServe devices and routes commands and results between the server and connected SIMServe instances.

The current implementation is an early development version focused on establishing a stable Server ↔ Serve communication layer.

## Current Status

**Release:** `v0.1.0`
**Protocol:** `v1`

### Implemented

- WebSocket connection between SIMServe and SIMServer
- Server-side Serve connection management
- Server-generated `serve_id`
- Serve registration handshake
- Command routing from SIMServer to a selected SIMServe
- Request/response correlation using `request_id`
- Result routing from SIMServe back to SIMServer
- `summary` command
- `history` command
- End-to-end testing using a real Android SIMServe device
- Local development test harness for CommandService

### Not Implemented Yet

- Persistent Serve identity
- Client application
- Serve ↔ Client pairing
- Authorization
- Authentication
- Cryptographic identity
- End-to-end encryption
- Encrypted transport
- User management
- Production security model

These are intentionally outside the scope of the current release.

## Architecture

The current communication flow is:

```text
                    WebSocket
        ┌─────────────────────────────────┐
        │                                 │
        ▼                                 │
   ┌──────────┐                    ┌──────┴──────┐
   │ SIMServe │                    │  SIMServer  │
   │ Android  │                    │   Python    │
   └────┬─────┘                    └──────┬──────┘
        │                                 │
        │  Command                        │
        │ ◄───────────────────────────────┤
        │                                 │
        │  Result                         │
        ├────────────────────────────────►│
        │                                 │
```

SIMServer currently acts as the command endpoint and connection manager.

SIMServe receives commands and executes them through its local `CommandService`.

The current architecture deliberately keeps the Server ↔ Serve protocol simple so that identity, pairing, and cryptographic layers can be introduced later without redesigning the basic command/result contract.

## Components

### SIMServer

The Python server is responsible for:

- accepting Serve WebSocket connections
- registering connected Serves
- assigning `serve_id`
- keeping track of active Serve connections
- routing commands to a selected Serve
- waiting for the corresponding result
- returning the result to the command caller

### SIMServe

SIMServe is the Android-side component.

It is responsible for:

- maintaining the WebSocket connection
- registering with SIMServer
- receiving commands
- executing commands through `CommandService`
- returning standardized results

Current SMS-related commands are implemented locally through:

```text
CommandService
    │
    ├── summary
    │
    └── history
```

## Protocol

The current protocol version is:

```text
Protocol v1
```

The protocol defines three connection-level/message types:

```text
register
registered
command
result
```

The complete protocol specification is documented in:

```text
docs/PROTOCOL.md
```

  "type": "command",

  "command": "summary",

  "created_at": "20260911122000",

## `serve_id`

In the current implementation, `serve_id` is generated by SIMServer when a SIMServe registers.

It is currently associated with the active Server-side connection.

Persistent identity is **not implemented in `v0.1.0`**.

The intended future behavior is for a SIMServe installation to retain a long-lived identity across:

- WebSocket reconnects
- application restarts
- device restarts

while a new identity is expected after application data is removed or the application is reinstalled.

This future identity will become the basis for Serve ↔ Client pairing and authorization.

## Security

The current development version does not provide a production security model.

The WebSocket connection currently uses:

```text
ws://
```

rather than:

```text
wss://
```

This is intentional for the current development stage.

The planned production architecture is based on end-to-end encryption between the authorized endpoints, with SIMServer functioning primarily as a router.

In that future architecture, SIMServer should not need access to the contents of commands or SMS data.

Authentication, authorization, key management, and cryptographic protocols have not yet been implemented and must not be inferred from the current protocol.

## Development

The current development process is intentionally incremental.

A typical feature should follow:

```text
Protocol
   ↓
Server
   ↓
SIMServe
   ↓
Local test
   ↓
End-to-end test
   ↓
Documentation
```

Server and Serve must remain compatible with the same protocol contract.

The Client does not exist yet and therefore is not part of the current compatibility matrix.

---

## Version Compatibility

The system consists of multiple independently versioned components:

```text
SIMServer version
SIMServe version
Client version
Protocol version
```

Software versions and protocol versions are separate concepts.

The current baseline is:

```text
SIMServer    0.1.0
SIMServe     0.1.0
Client       —
Protocol     v1
```

Future releases may allow different Server, Serve, and Client software versions as long as they support a compatible protocol version.

---

## Development Checkpoint

`v0.1.0` is the first stable development checkpoint for the Server ↔ Serve communication pipeline.

At this point the following complete path has been verified:

```text
SIMServe
   ↓
WebSocket
   ↓
SIMServer registration
   ↓
serve_id
   ↓
HTTP command
   ↓
WebSocket command
   ↓
SIMServe CommandService
   ↓
SMS functionality
   ↓
result
   ↓
SIMServer
```

This release should be treated as the baseline before implementing persistent identity, pairing, authorization, and cryptographic communication.
