# Architecture Decisions

## 1. Server Generates `serve_id`

`serve_id` is generated by SIMServer rather than SIMServe.

Reason:

- Server controls the namespace.
- The Server can guarantee uniqueness.
- SIMServe does not need to generate globally unique identifiers.

The current implementation associates the generated ID with the active connection.

### Important future change

`serve_id` is intended to become a long-lived identity rather than a WebSocket session identifier.

The desired lifecycle is:

```text
Initial installation
    ↓
new identity

Application restart
    ↓
same identity

Device restart
    ↓
same identity

WebSocket reconnect
    ↓
same identity

Application data removal
    ↓
new identity

Application uninstall/reinstall
    ↓
new identity
```

Persistent identity is not implemented in `v0.1.0`.

---

## 2. `serve_id` Is Routing Metadata

`serve_id` is currently used by SIMServer to select a connected Serve.

It is deliberately not part of the Command payload.

The HTTP command request contains:

```json
{
  "serve_id": "...",
  "request_id": "...",
  "command": "...",
  "data": {}
}
```

SIMServer removes the routing concern before sending the actual Command protocol message over WebSocket:

```json
{
  "type": "command",
  "request_id": "...",
  "command": "...",
  "created_at": "...",
  "data": {}
}
```

This keeps the Serve-side protocol independent from Server routing.

---

## 3. No Protocol Adaptation Between Server and Serve

The Server and Serve use the same Command/Result contract.

SIMServer should not transform command payloads into a different Serve-specific format.

SIMServe should not transform results into a different Server-specific format.

The intended path is:

```text
Server Command
      ↓
WebSocket
      ↓
SIMServe CommandService
      ↓
Command Result
      ↓
WebSocket
      ↓
Server
```

This is important for future Client integration and for eventual cryptographic wrapping of messages.

---

## 4. `request_id` Is the Correlation Identifier

Each command has a `request_id`.

The corresponding result carries the same `request_id`.

Example:

```text
Command:
request_id = abc123

Result:
request_id = abc123
```

This allows SIMServer to maintain multiple outstanding requests and match each result to the correct request.

---

## 5. Command and Result Are Different From Connection Registration

Registration is connection-level protocol behavior:

```text
register
    ↓
registered
```

Commands are application-level behavior:

```text
command
    ↓
result
```

SIMServe therefore handles registration responses inside `RemoteConnection`, while normal commands are forwarded to `CommandService`.

This separation should be preserved.

# Current Commands

## `summary`

Returns a conversation-level SMS summary for a selected SIM.

Current input:

```json
{
  "type": "command",
  "request_id": "test-summary-001",
  "command": "summary",
  "created_at": "20260911122000",
  "data": {
    "sim": 0
  }
}
```

---

## `history`

Returns SMS history for a selected SIM and number.

Current input:

```json
{
  "type": "command",
  "request_id": "test-history-001",
  "command": "history",
  "created_at": "20260911122000",
  "data": {
    "sim": 0,
    "number": "+49123456789",
    "start": "2026-01-01 00:00:00",
    "end": "2026-01-02 00:00:00"
  }
}
```

Date handling and optional date semantics remain an area for refinement.

# Security Decisions

Security hardening is intentionally deferred.

Current development communication uses:

```text
ws://
```

rather than `wss://`.

This is intentional because the eventual production design is expected to provide end-to-end cryptographic protection rather than relying only on transport encryption.

The desired future model is:

```text
Client
   │
   │ encrypted
   ▼
SIMServer
   │
   │ encrypted / routed
   ▼
SIMServe
```

SIMServer should eventually operate primarily as a router and should not be able to read the application payload.

The following are therefore future milestones:

1. Persistent identity.
2. Serve identity verification.
3. Client identity.
4. Pairing.
5. User-approved authorization.
6. Key synchronization/exchange.
7. Message authentication/integrity.
8. End-to-end encryption.

No production security guarantees should be inferred from `v0.1.0`.

# Version Compatibility

Server, Serve, and Client are separate software components.

Protocol compatibility is independent from software version.

Current matrix:

| Component | Version | Status          |
| --------- | ------: | --------------- |
| SIMServer |   0.1.0 | Implemented     |
| SIMServe  |   0.1.0 | Implemented     |
| Client    |       — | Not implemented |
| Protocol  |      v1 | Implemented     |

Any future incompatible protocol change must result in a new protocol version.

# Next Milestone

## Persistent Serve Identity

Goals:

- Generate identity only during initial registration.
- Persist identity on SIMServe.
- Reuse identity across reconnects.
- Persist Serve records on SIMServer.
- Separate persistent identity from active WebSocket connection state.
- Preserve routing through `ServeManager`.
- Test Server restart and Serve reconnect behavior.

The expected architecture is:

```text
                 Persistent
                 identity
                    │
                    ▼
              ServeRepository
                    │
                    │
                    ▼
serve_id ───── ServeManager
                    │
                    ▼
             active WebSocket
```

`ServeManager` should remain responsible for live connections rather than becoming the persistent identity database.

---

# Checkpoint Rule

`v0.1.0` should be treated as a safe rollback point before beginning persistent identity, pairing, and cryptographic work.

Any future architectural change that significantly modifies the protocol or identity model should be documented here before implementation.
